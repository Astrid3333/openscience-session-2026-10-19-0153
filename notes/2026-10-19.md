# 2026-10-19 — auditoria tool-by-tool de octave-mcp

Objetivo: probar `octave-mcp` tool por tool y encontrar bugs / inconsistencias
entre el catálogo publicado y las tools realmente invocables.

## Que se hizo

- Recorrido por `octave_list_tools` + `octave_get_tool_schema` + `octave_call_tool`
  sobre tools representativas (octave_run, linear_algebra, compute_math_pipeline,
  ocas_symbolic, workspace_validate, octave_syntax, semantic_bridge, compute_gradient_hessian…).
- Sondas puntuales de las tools legacy que fallaban.
- Barrido completo de dispatch: import de `server.py` como módulo + chequeo de
  `tool_registry.get_handler(nombre)` para las 362 entradas del catálogo `TOOLS`.
- Corrida de la suite oficial `run_all_validations.py --verbose` (151.7 s).

## Hallazgos

### H1 — 3 tools anunciadas pero invocables = NO (bug de dispatch)

`tools/list` devuelve solo las 3 meta-tools (META_TOOLS, server.py:446-477).
El bridge `call_tool` (server.py:543-584) solo tiene fallback explícito para
`octave_run`, `octave_eval_expr`, `octave_run_script`, `octave_version` y luego
lanza `Tool '{target}' no encontrada`. **No cae a la cadena legacy ni a
`tool_registry`.**

Resultado: de las 362 tools del catálogo, 7 no tienen handler en el registry;
4 están salvas por el fallback explícito; quedan **3 inalcanzables**:

- `run_octave`
- `run_math_pipeline`
- `numeral_systems_embedding`

Las tres SÍ aparecen en `list_tools` y SÍ tienen `get_tool_schema` → inconsistencia
catálogo/invocación confirmada.

### H2 — La suite de validación no puede correr en este entorno

`run_all_validations.py` (líneas 242, 300, 340) y `health_check_tool.py`
(líneas 117, 149) spawnean `["python3", SERVER_PATH]` en vez de
`[sys.executable, SERVER_PATH]`. `python3` = sistema, sin `ocas` →
`ModuleNotFoundError: No module named 'ocas'` desde `server.py:82` →
`ERROR FATAL: no se pudo obtener tools/list`.

Workaround usado (sin tocar el repo): shim en PATH
`/tmp/opencode/pyshim/python3` que hace `exec .../.venv/bin/python "$@"`.

### H3 — Resultado real de la suite con el shim (365 tools, 347 evaluadas)

- PASSED: 339
- FAILED: 2 — `attractor_trajectory` (check mariposa: `d_final=0.1795` < umbral 1.0),
  `fem_electromagnetic_tool` (falta binario Rust)
- ERROR: 6 — `cfd_tool`, `bem_electromagnetic_tool` (binarios Rust ausentes),
  `dft_tool` (falta `.venv-pyscf`), `compute_hilbert_transform`
  (Octave sin paquete `signal`), `numeral_systems_embedding` (H1),
  `frame_analysis_tool` (responde OK pero sin campo `validation_passed` →
  viola el contrato que la suite espera)
- SKIPPED: 18 (sin `validate` en el enum; `run_math_pipeline` excluido a propósito)

### Infra comprobada

  `submotors/{cfd_cavity,bem_electromagnetic,fem_poisson2d}/target/release/` no existe.
- `.venv-pyscf` no creado.

### Casi-accidente

Crear el shim con `printf > /tmp/opencode/pyshim/python3` sobre un symlink
resolvió hasta `/usr/bin/python3.12` y falló con Permission denied.
No se corrompió nada (ELF intacto), pero es una trampa real:
**nunca redirigir a un path que puede ser symlink.**

## Lecciones

1. En un servidor MCP con meta-dispatch, cada rama legacy nueva necesita
   registro en `tool_registry` o el meta `call_tool` no la ve — el catálogo
   (`list_tools`) no es prueba de invocación.
2. Cuando una suite use `python3` hardcodeado, preferir `sys.executable`;
   mientras tanto un shim en PATH es un workaround no invasivo.
3. Probar tools por `validate` no detecta tools sin `validate` en el enum:
   el alcance del test es el schema, no el catálogo.
